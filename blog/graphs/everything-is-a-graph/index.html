Graphs, Graph Compilers and the Verification of High-Performance KernelsPart 1Nov 11, 2026

Everything is a graph

Compilers represent control flow, data dependencies and tensor computations as graphs. The software engineer meets these graphs in program analysis, the AI engineer behind a PyTorch model. This essay takes both points of view and asks what each graph records.

This is the introduction to a series on graph compilers. A background in compilers or in machine learning modeling helps. Sections 1 and 2 cover program analysis, Section 3 the AI engineer's graph, Section 4 Rust, and Section 5 verification.

Modular recently released the MAX graph compiler with its source. That makes this a good time to go deeper into graph abstractions in AI, especially for inference and for kernel verification. Gang of four: C++, Rust, Lean and Mojo discussed the release at a high level, and this series reads it closely.

1. Program analysis: a program as a graph

A control-flow graph makes the possible transfers of control explicit: an edge from one block of statements to another means that the second can run right after the first. Figure F1 draws three graphs of one small Python program. A function f adds one to its argument, branches, calls g on one branch, assigns a constant on the other and returns. Function g doubles its argument.

The left drawing is Allen's control-flow graph of 1970: four blocks and the two outcomes of the branch. The middle drawing is static single assignment (SSA). Each variable is assigned exactly once, and a phi node at the join picks y1 or y2 by the edge taken. Definitions and uses become edges, drawn in green, and constant propagation, dead-code elimination and register allocation walk them. The renaming has a second reading, from Appel's SSA is Functional Programming: a variable assigned once is a let-binding, a block is a function, and a phi node is its parameter. The right drawing joins f and g into one supergraph with a call edge and a return edge. With several callers, a supergraph also contains paths that no execution takes: into g from one caller and out to another.

In 1995 Reps, Horwitz and Sagiv published Precise Interprocedural Dataflow Analysis via Graph Reachability. Figure F2 draws their construction for one query: the argument a of f is tainted, and we want every place the taint reaches. A second function, h, also calls g.

The construction has three moves. First, explode the graph. A node becomes a pair of a program point and a fact, and an edge is one statement turning one fact into another, as x = a + 1 turns a into x. Second, if every statement's effect distributes over union, nothing is lost, and the dataflow fixpoint becomes plain reachability. Third, count only realizable paths, those whose returns match their calls.

The blue path is realizable: the taint enters g on f's call edge and leaves on f's return edge. The red route enters from h and returns into f, which no execution does. A summary edge, drawn in gold, records which facts leave a call for one fact that enters it, and it is reused wherever that fact arrives. The cost is bounded by the supergraph's edges times the cube of the number of facts, for the class the paper names IFDS: interprocedural, finite, distributive, subset. A realizable path may still take a branch that no input takes.

Once a program is a graph, a question of this class is a reachability question, and the algorithm is independent of the source language. Facts are nodes, derivations are paths, and precision is the choice of which paths are allowed. Figure F3 places the result among its neighbours.

An analysis makes several choices, and they are separate. Steensgaard's and Andersen's points-to analyses both ignore statement order and calling context. They differ in how they merge: Steensgaard unifies and is almost linear in program size, and Andersen keeps subset constraints and is cubic in the worst case. Classical dataflow follows statement order inside one procedure. IFDS adds calling context, at the bound above with its two variables. Symbolic execution also follows the branch taken and pays for it path by path.

Figure F3's red note is the scope of the model. Each analysis answers only for the code its graph contains. Code behind a foreign function interface (FFI), such as native code under Java or a C++ kernel under Python, needs an analyzed body or a summary. One way to get that body, whole-program LLVM IR from link-time optimization (LTO) analyzed with PhASAR, is out of scope.

Figure F3's last row is where the series ends. Figure F4 asks one property of f, that it never returns a negative number, in four ways.

A test runs one input. With a = 5 the true branch returns 12 and the false branch never runs. Symbolic execution replaces the input with a symbol: each path carries its condition and a formula for its result, but paths multiply at every branch. Concolic execution is a concrete run that also collects symbolic constraints. It records the branch condition of the a = 5 run as a formula, negates it, asks an SMT solver for an input, gets a = -1, one possible answer, and runs the other branch.

Verification states the property and asks the solver for a counterexample. We ran the two paths of f in the Z3 solver, over the integers. On both, y < 0 is unsatisfiable, which proves the property for every input of this loop-free model. A timeout or the answer unknown would have left the question open.

2. Jitana and ReHAna: a graph that is agnostic to its source

Our earlier research, summarized on the research page, belongs to this line of work. Jitana (2019) and ReHAna, which extends it, are not a row of Figure F3. They are the engineering under such analyses, turning the Dalvik bytecode of an Android application into graphs. Figure F5 draws those graphs for one small application.

Jitana's virtual class loader admits a class when reachability finds it, by the Android virtual machine's own algorithm. It decodes the class's DEX file into the graphs of the virtual machine: class loaders, classes, methods, fields and instructions. A method's instruction graph is the control-flow graph of Figure F1. Analyses read the decoded instructions, annotate these graphs and build analysis graphs of their own: a pointer assignment graph, a context-sensitive call graph and a graph of communication between applications. The call graph and the instruction graphs give the supergraph of Section 1.

The graphs can take in code that arrives late. Android applications load code at run time through reflection and dynamic class loading. ReHAna admits such a file through a child loader with its own parent edge and extends the analysis in place. Nodes and paths already found remain. Conclusions that depend on the graph being complete, such as the set of targets of a call, are computed again.

In Jitana's Facebook case study the analyzed classes grew from 3,918 to 23,621 after three DEX files loaded at run time were captured. In ReHAna's 2018 sample of 60 popular applications, static analysis found reflection or dynamic loading in 34. Native code behind the Java Native Interface is not analyzed, which is the FFI limit of Section 1 in practice.

The series takes one property from this work: the graph is agnostic to its source. Figure F6 draws the two routes.

Both lanes have one architecture: a builder makes a graph, rules run on it, and results come out. The rules may build further graphs, as Jitana's analyses and a compiler's passes both do. The lanes differ in what the builder establishes about its graph. Jitana's loader follows the virtual machine's loading algorithm, so the graph holds the classes that the virtual machine would load. A tracer follows the frame it was given, and what its graph covers depends on whether it traced abstract values or recorded one run.

3. Graph compilers from the AI engineer's PoV

An AI engineer seldom builds a graph by hand, because the framework records one. Raschka's one-hour introduction to PyTorch draws a model as a computation graph, a directed graph of the operations in a mathematical expression. His example is a logistic regression: x1 times w1, plus b, through a sigmoid, into a loss. Figure F7 redraws his diagram with its values and gradients.

The forward computation has definitions and uses, as SSA does: a tensor is a definition, and each edge into an operation is a use. When gradients are tracked, PyTorch also records a backward function for each operation, with the values that function needs. Backward walks these functions in reverse from the loss, applies the chain rule and adds the contributions reaching each leaf.

This graph exists for gradients and does not make the model faster. A CUDA graph can. Take a minimal model, relu(x @ w + b): a matrix product, an add and an activation. In PyTorch's default mode each operation makes its own trip to the GPU, drawn in Figure F8. Python runs the line. A dispatcher picks the kernel for the device and data type. ATen, the C++ tensor library inside libtorch, checks shapes, allocates the output and sets up arguments. The CUDA driver launches the kernel. The next line repeats all of it, and for a small model this friction can cost more than the arithmetic.

A CUDA graph removes the friction. PyTorch runs the step once with the CUDA stream capturing, so the kernel launches and their arguments are recorded, not executed. Every later step replays the record with one call, which skips argument setup and kernel dispatch in Python, C++ and the driver. An edge of this graph only orders two launches. The simple capture shown needs static shapes, static control flow and buffers at fixed addresses, since the record holds the branch taken and the pointers passed.

A CUDA graph only replays: the kernels stay the same. A graph compiler rewrites a graph of operations, for example by fusing the add and the activation into one kernel, and lowers it to kernels and a plan to run them. To rewrite operations it must hold several of them before they run. There are three ways to get them: build the graph explicitly, trace the program, or defer execution. Figure F9 draws the third beside eager execution.

Eager execution submits each operation when its Python line runs. It is PyTorch's default, which is why a model can branch on a tensor's value or change a shape on any line. Lazy execution splits the two events: the line records the operation and returns a handle, and work starts when a value is demanded.

Laziness alone is not faster, because delayed work is the same work. The gain comes when a compiler holds the record before it runs, so it can fuse the add into the activation and specialize both to the shapes it saw. Keeping the compiled result for later calls is a further choice, and it needs a condition, because the compiler saw one set of inputs. Figure F10 shows such a condition in torch.compile, which traces a function when it is called and is not a lazy tensor system.

TorchDynamo hooks the interpreter's frame evaluation. On the first call it traces the Python frame into an FX graph and writes guards. A guard is a condition the trace relied on: a tensor's shape, its data type, or a Python integer that chose a branch. TorchInductor compiles the graph into Triton or C++ kernels, and Dynamo stores the result as an entry for that frame.

On each later call Dynamo runs the guards of the stored entries. If an entry accepts the call, its compiled code runs. If none does, Dynamo traces and compiles again and stores another entry. Limits bound the number of entries a frame collects. Past a limit, stored entries still serve the calls they accept, and other calls run uncompiled.

Figure F11 draws torch.compile beside two other routes.

In the middle lane, JAX's jit traces a function on abstract values into a jaxpr, a functional program of let-bindings in Appel's sense, specialized to array shapes, types and any static argument values. The jaxpr is lowered to StableHLO and handed to XLA, which fuses operations and emits an executable for the device. A call matching no stored specialization is traced again.

In the bottom lane the graph is built before anything runs: Python stages operations into a MAX graph, and a pipeline of dialects lowers it to a compiled model. Each route has a reuse condition, a rule for when a stored graph or compiled artifact may serve a call, and the three are checked at different stages. Dynamo runs guards at every call. JAX matches each call against stored specializations. MAX looks up a key when a graph is compiled, and its shape checks run with the model.

MLIR, LLVM's framework for defining intermediate representations through dialects, enters these stacks at different levels. JAX lowers a jaxpr to StableHLO, an MLIR dialect. MAX's graph compiler uses MLIR dialects throughout. In PyTorch's usual compilation path, TorchDynamo captures an FX graph, and TorchInductor generates GPU kernels in Triton. MLIR enters this path inside the Triton compiler.

torch-mlir provides a different route: it imports PyTorch programs into MLIR for downstream compilers. It is a separate LLVM incubator project, not a stage in the TorchInductor-to-Triton pipeline.

Figure F12 draws the MAX route in three phases, as we read it in the source and its design document. For further viewing, Modular has two talks: MAX's Graph Compiler Internals with Feras Boulala and MAX Graph Compilation to Execution.

Compile comes first. Python builds the graph in RMO, the relaxed dialect, whose operators have no verifiers based on shape. The compiler computes a key over the graph and its options and looks it up. A hit returns stored bytes and skips lowering and code generation. On a miss, lowering to MO makes every operator strongly typed and inserts rebinds, shape checks that run with the model. MAP turns operations into loops and kernels, and fusion is decided there. MOGG holds the routine that becomes Mojo, and MGP holds the model as a program with buffers and an order. The kernels are compiled, the model is serialized, and the two form the MEF artifact, the bytes the runtime is given.

Load is the second phase: the runtime reads the bytes and initializes a model. Execute is the third and repeats on every call: the runtime schedules the model's steps on the host and launches kernels on the CPU or GPU.

4. Rust: Candle, Burn and cuTile-rs

All three routes start in Python. Figure F13 shows the same route in Rust.

Candle, from Hugging Face, is eager. A tensor method goes through storage to a backend (CPU, CUDA or Metal) and runs a kernel. When that kernel is compiled depends on the backend: we read that the CUDA kernels are built when the crate is built, and that the Metal backend compiles its kernel source on first use. When gradients are wanted, a forward call also records what backward will need, and nothing rewrites the forward operations. Burn puts a graph back at run time when its Fusion layer is on and the backend supports it. Fusion queues tensor operations in a stream, stores plans for the sequences it has seen, and joins supported groups of operations into kernels. The kernels come from CubeCL, a compiler for kernels written in Rust that targets CUDA, Metal, Vulkan and WebGPU.

cuTile-rs, in NVIDIA's cuda-rust repository, has no tensor graph from a framework. The programmer writes the kernel as a Rust module over tiles of an array. The Rust compiler type-checks it and builds its launcher. When a launch finds no compiled kernel in its cache, a second compiler lowers the same source to CUDA Tile IR and then to GPU code. Rust removes Python, not the question of who holds a graph of operations: in Candle no component does for the forward pass, in Burn a stream at run time, in cuTile-rs the programmer.

5. Formal verification of kernels

Kernels are increasingly generated, by compilers such as TorchInductor and now by AI agents. Gimlet Labs show what can go wrong in Formally Verifying AI-Generated GPU Kernels. Their talk GPU Kernel Formal Verification is further viewing.

In their example an agent rewrites an attention kernel and drops a clamp the reference applies before the softmax. Random inputs rarely reach the clamp, so the faster kernel passes its tests and is wrong. Their checker is the last column of Figure F4 applied to tensors. It recovers one graph of expressions from the PyTorch reference and one from the Triton kernel, makes the inputs symbolic, and asks the Z3 solver for an input where they differ. On 26 Triton kernels from KernelBench the authors report 16 proved equivalent, 2 that passed numeric tests and were proved different, and 8 undecided.

The proofs treat numbers as exact reals and expand reductions up to a bound, at fixed shapes, so they do not establish that the deployed kernels agree in floating point. A proof about recovered graphs also leaves memory safety, data races and the compiler below it open. The check is a graph question: a kernel can be verified against its graph only when someone can say what that graph is.

6. Next in the series

The series follows two small Python programs from Python to a kernel. The first is the model of Figure F8: three operations, fixed shapes and an answer that can be checked by hand.

def block(x, w, b):
    return relu(x @ w + b)

The second adds one step of attention over keys and values that grow by a row per token, so its shapes change on every call.

def step(x, w, b, k, v, mask):
    h = relu(x @ w + b)
    return softmax((h @ k.T) * 2**-0.5 + mask) @ v + h

Here h has shape (1, 2), and k and v have one row per stored token and width 2, the width that the scale 2**-0.5 belongs to. The softmax runs over the stored tokens, and the caller appends a row to k and v between steps.
