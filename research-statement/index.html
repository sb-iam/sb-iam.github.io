My research develops just-in-time abstractions for software: program representations that are constructed and refined incrementally as analysis requires them. The purpose is to support static verification of program properties and their validation on observed executions.

Research Area
Hybrid program analysis

Static analysis conventionally assumes a closed world, in which all of the code is present before analysis begins. The assumption fails wherever code is loaded, generated or compiled at run time. For example, in one release of Facebook for Android we found 3,918 classes by static analysis and 23,621, six times as many, after capturing three files that the app loaded as it ran. A closed-world analysis can take such code into account only by starting again.

Jitana and ReHAna

Jitana and ReHAna, our frameworks for hybrid program analysis on Android, remove the assumption. They combine static analysis with observation of the app as it runs, and their design is modeled on two mechanisms of a language virtual machine: the class loader, which loads a class only when it is needed, and the just-in-time compiler, which analyzes one method at a time.

Jitana's Class-Loader Virtual Machine is a virtual graph loader: it models the class loaders of the device and loads a class into its graphs only when reachability analysis or the running app requires it. Because a class is identified by its loader and its name, the classes of many apps remain distinct in one analysis (Figure F1). One such analysis covered the 129 apps on a tablet, two million methods in all, in 19 minutes.

ReHAna's Virtual Class-Loader follows the class loader of a running app. When the app loads classes through reflection or dynamic code loading, ReHAna adds their analysis to the existing graphs, so that the cost of analysis is proportional to the code that is new. Across 21 apps, ReHAna slowed execution by a factor of at most 1.32, whereas StaDynA, an earlier hybrid analysis for the same task, slowed it by as much as 5.71.

JITAC: Just-in-Time Abstractions for Code

Four principles of the virtual graph loader can be stated without reference to Android.

  1. A unit of code is identified by its namespace and its name.
  2. Only the loader creates nodes, and only when a unit is required.
  3. Static results and observations of the running program are recorded on the same nodes.
  4. When a unit is added, analysis resumes from the new nodes.

JITAC takes these principles from the virtual graph loader to a virtual incremental loader, whose unit may be a shared library, a kernel of a compiled model, a class or a container image (Figure F2). The four kinds of unit stand for the four levels that my work addresses above the Application Binary Interface (ABI): systems code, the compiler, the application and the cluster.

C++, Rust, Lean and Mojo

C++, Rust, Lean and Mojo are the first-class languages of this research: the work is written in these four, and code in any other language is generated from them. Each has its own task (Figure F3). Lean states an abstraction and the properties claimed of it. Mojo, which is built on MLIR, implements it on heterogeneous hardware. C++ and Rust connect it to existing systems, because LLVM and MLIR are written in C++ and both Android and the Linux kernel accept Rust.

Current Direction

My dissertation carries the method from Android to neural network models compiled by MAX, a framework from Modular whose kernels are written in Mojo: static analysis predicts the behavior of an execution, the execution is observed, and the two are reconciled. The measured results in this statement are those of Jitana and ReHAna; JITAC is under construction and has not yet been evaluated, and papers on it are in preparation.
